# M18 — Checklists

## Monthly Tactic Selection Checklist

- [ ] Tactic bank reviewed by category (`resources.md`)
- [ ] Each candidate tactic scored Impact (1–5) × Effort (1–5)
- [ ] 3–5 tactics selected for the month, prioritizing highest Priority Score
- [ ] Each selected tactic reframed as a testable hypothesis (Method 2 in `methods.md`) with a defined success metric
- [ ] Execution owner assigned per tactic (who's actually running it — often the owning M09–M17 stage's team)
- [ ] Tracker row created for each tactic with a 30-day decision date

## Pre-Execution QC Gate

- [ ] Tactic doesn't conflict with the standing QC rules of the channel it runs through (e.g., an email tactic still respects M17's human-review gate if it involves AI-drafted copy)
- [ ] No fabricated claims baked into the tactic's execution (e.g., a "case study post" tactic only runs if a real case study exists — per the Implementation Plan's standing no-fabrication rule)
- [ ] Budget/resource requirement confirmed before starting, for any tactic in the Paid & Distribution category

## 30-Day Test Window (Default)

- [ ] Fixed 30-day window applied unless the tactic's own natural cycle is longer (e.g., a referral program's Day-60 email trigger runs on its own cycle, not compressed to 30 days)
- [ ] Metric tracked consistently across the full window — no cutting the test short because early results look good or bad
- [ ] Any confounding factor noted (e.g., another campaign running at the same time) so the result isn't misread

## Decision Checklist (Scale / Iterate / Kill)

- [ ] Result measured against the original hypothesis's defined success metric — not a different metric picked after the fact
- [ ] **Scale** — tactic clearly worked: written into the owning M09–M17 stage's `methods.md` as a standing practice; tracker row marked "Scaled"
- [ ] **Iterate** — result was inconclusive or partially positive: adjusted version re-tested next cycle; tracker row marked "Iterating," with the adjustment noted
- [ ] **Kill** — tactic didn't work: tracker row marked "Killed" with a reason, kept in the log rather than deleted, so it isn't blindly re-tested later
- [ ] Result logged in the Experiment Tracker regardless of outcome — a killed tactic is still a data point

## Cross-Stage Handoff Checklist (When a Tactic Graduates)

- [ ] Relevant M09–M17 stage's `methods.md` updated with the new standing practice
- [ ] Relevant M09–M17 stage's `checklists.md` updated if the new practice introduces a new QC step
- [ ] M18's own tracker row cross-linked to the destination stage, so the origin of the practice stays traceable
